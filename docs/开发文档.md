## 1. 产品决策回顾

| 决策项 | 结论 |
|---|---|
| 运行形态 | 第一阶段本地全栈（Mac 本地服务 + SQLite），架构预留云端接口 |
| 手机访问 | 本地服务绑 `0.0.0.0`，同 WiFi 下手机浏览器直接访问（数据不出内网） |
| 隐私 | 数据只存本机，`data/` 不进 git，不调用任何外部服务 |
| 求职方向 | 销售 / 运营 / 市场三线，「主打一个 + 其余备选」，主方向在设置页配置 |
| AI 能力 | 双通道：① 离线（默认）导出 prompt → AI 对话跑 → JSON 回填；② 在线（可选）自填 LLM key 应用内直连。写入同一张结果表，用 `source` 区分 |

## 5. 状态机（投递流转）

**状态枚举**：`意向 → 投递 → 笔试 → 面试 → offer → 关闭`

**允许流转（白名单，前后端双重校验，禁止跳阶段）**：
- 意向 → 投递
- 投递 → 笔试 / 面试 / 关闭
- 笔试 → 面试 / 关闭
- 面试 → offer / 关闭（多轮面试时状态保持在「面试」，轮次记在 interview 表）
- offer → 关闭（终态外唯一出口）
- 关闭 → （终态，不可再流转）

**提醒规则（打开工作台即计算，不做后台常驻推送）**：
1. 投递进入后满 7 天仍无进展 → 提醒跟进
2. 面试日 +1 天 `result` 仍空 → 提醒复盘
3. offer 后 3 天未决 → 提醒决策
4. `contact.next_followup_at` 或 `application.next_followup_at` 到期 → 提醒

## 6. API 接口设计

> 统一前缀 `/api`，JSON 交互；错误返回 `{error, code}`。
> 所有写操作经 repository 层，便于将来换云端实现。

### 简历 resume
- `GET /api/resumes` 列表（按 direction 过滤）
- `POST /api/resumes` 新建（含文件上传 multipart）
- `GET /api/resumes/{id}` 详情
- `PUT /api/resumes/{id}` 编辑
- `DELETE /api/resumes/{id}` 删除
- `POST /api/resumes/{id}/file` 上传/替换简历文件（触发解析）

### JD
- `GET /api/jds` 列表（status / direction 过滤）
- `POST /api/jds` 粘贴新建（raw_text 入库）
- `GET /api/jds/{id}` 详情（含 parsed_json）
- `PUT /api/jds/{id}` 编辑
- `DELETE /api/jds/{id}` 删除

### 投递 application
- `GET /api/applications` 列表（status / direction / contact 过滤）
- `POST /api/applications` 新建（**必须带 resume_version_id**）
- `GET /api/applications/{id}` 详情（含关联 interview 列表）
- `PUT /api/applications/{id}` 编辑
- `POST /api/applications/{id}/transition` 状态流转（body: target_status，后端白名单校验）
- `DELETE /api/applications/{id}` 删除

### 面试 interview
- `GET /api/applications/{id}/interviews` 某投递的面试列表
- `POST /api/interviews` 新建（含 questions / interviewers）
- `PUT /api/interviews/{id}` 编辑
- `POST /api/interviews/{id}/review` 提交复盘（body 含 feedback / unanswered_questions / result）
- `DELETE /api/interviews/{id}` 删除

### 题库 question
- `GET /api/questions` 列表（按 direction / category 过滤）
- `POST /api/questions` 手动新增
- `DELETE /api/questions/{id}` 删除

### 人脉 contact
- `GET /api/contacts` 列表
- `POST /api/contacts` 新建
- `PUT /api/contacts/{id}` 编辑（含更新 last_contact_at / next_followup_at）
- `DELETE /api/contacts/{id}` 删除

### 技能 skill
- `GET /api/skills` 列表
- `POST /api/skills` 新建（source 区分来源）
- `PUT /api/skills/{id}` 编辑
- `DELETE /api/skills/{id}` 删除
- `POST /api/skills/{id}/log` 打卡（body: log_date, note）
- `GET /api/skills/{id}/logs` 打卡历史

### 匹配 match
- `POST /api/match` 计算匹配（离线：返回 prompt；在线：直连算分）→ 写 match_result
- `GET /api/jds/{id}/matches` 某 JD 的所有匹配记录

### AI 双通道 ai
- `POST /api/ai/export-jd-parse` 入参 jd_id → 返回结构化 prompt 文本（用户粘到 AI 对话跑）
- `POST /api/ai/export-match` 入参 jd_id + resume_version_id → 返回匹配 prompt
- `POST /api/ai/export-interview-q` 入参 direction_tag → 返回面试题生成 prompt
- `POST /api/ai/import-result` 接收 JSON 回填（**schema 校验 + 友好报错**，脏数据拒绝入库）

### 驾驶舱 stats
- `GET /api/stats/funnel` 漏斗转化率（各状态数量 + 转化率）
- `GET /api/stats/direction` 三方向效果对比（各方向投递数/面试率/offer率）
- `GET /api/stats/resume-versions` 简历版本效果对比（各版本带来的面试/offer）
- `GET /api/stats/overdue` 逾期跟进聚合（投递/面试/人脉）

### 设置 settings
- `GET /api/settings` 读取
- `PUT /api/settings` 更新（主方向、LLM 开关/key）

### 备份 backup
- `POST /api/backup/export` 导出全表 JSON + 投递/联系人 Excel 到 data/backups/
- `GET /api/backup/files` 列出备份文件

## 7. 模块实现要点

| 模块 | 要点 |
|---|---|
| 简历库 | 多版本；上传 docx/pdf 自动解析文本存 parsed_text；版本必填绑定投递 |
| JD 库 | 粘贴 raw_text → AI 解析或手填 → parsed_json 结构化字段 |
| 投递看板 | 看板式六状态，拖拽触发 transition 接口（后端白名单校验）；必填仅 4 项：公司/岗位/简历版本/方向 |
| 面试中心 | 轮次/日程/面试官/问题/复盘；复盘提交时未答题自动入 skill + 高频题入题库 |
| 成长与人脉 | 技能差距三来源打通（匹配缺失/面试复盘/自评）+ 打卡；联系人跟进周期提醒 |
| 驾驶舱 | 漏斗、方向对比、版本对比、逾期聚合，首页加载即算 |
| AI 双通道 | 三类 prompt 模板导出 + JSON 回填校验；settings 预留 LLM key 在线开关 |

**两条闭环（核心价值，必须做通）**：
1. 匹配 → 简历：`match_result.missing_points` → 生成简历优化待办 → 新版本 → 重新匹配
2. 面试 → 技能：复盘里 `unanswered_questions` → 自动生成 skill gap 项 → 进学习计划 → 打卡

## 8. AI 双通道协议

**离线（默认，零 key、零费用、数据不出本机）**：
1. 工作台点「导出解析/匹配/面试题」→ 后端组装结构化 prompt（含 JD 文本、简历文本、方向等）→ 返回纯文本
2. 用户粘到 AI 助手对话跑 → 拿到结果
3. 工作台「导入结果」→ 粘贴 JSON → `POST /api/ai/import-result` 做 schema 校验后入库

**在线（可选）**：settings 填 LLM key 并开启 → 同类接口直接调用，结果同表存储，`source=在线`

**回填 JSON schema（示例，缺字段/类型错即报错）**：
```json
{
  "type": "jd_parse | match | interview_q",
  "jd_id": 12,
  "resume_version_id": 3,
  "result": { "...": "依 type 不同" }
}
```

## 10. 分阶段计划与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 骨架** | venv+依赖、建表、FastAPI 骨架、Vue 脚手架、start.sh、gitignore、git 初始化 | 一条命令起服务，同 WiFi 手机能开空页面 |

| **P2 面试中心** | 面试日程/轮次/复盘/题库 | 复盘后未答题自动进技能、高频题入库 |
| **P3 成长与人脉** | 技能差距+打卡、联系人跟进 | 三来源打通、逾期提醒生效 |

| **P6 收尾** | 备份脚本、launchd 自启、局域网说明、使用手册 | 备份可恢复、开机自启可用 |

**顺序原则**：P1 做完即开始真实使用，后续边用边加，避免「全做完才用」脱离实际。

## 11. 风险与待确认

1. `application.resume_version_id` 必填 —— 否则版本效果对比失真。
2. AI 回填 JSON 漂移 —— 必须 schema 校验 + 明确报错。
3. 状态机跳阶段 —— 白名单校验，前端禁用非法拖拽。
4. 方向标签手填 —— 枚举约束。
5. 录入成本 —— 必填压到 4 项以内，其余可后补。
6. 在职时间现实 —— P1 交付后先跑真实数据再迭代。
7. **待你确认**：当前已写的 ~790 行后端骨架（schema/models/repo/三个 service）是否保留作为 P0/P1 基础，还是全部回退重写？文档与现有骨架一致，建议保留。
